## 改造 A: 句子级 TF-IDF 替换 Jaccard

### 目的
`StenGraphPipeline._score_sentences` 在没有 sentence-level FAISS
时回退到 token Jaccard。Jaccard 对"短、稀有的关键实体"（人名/地名）
不友好——比如 query "Who created the show that featured Triumph
the Insult Comic Dog?" 里的 "Triumph"/"Insult" 在 Jaccard 里权重
和 "the" 一样低。

### 改动
1. `src/sentence_graph.py` — `SentenceNode` 加 `tfidf_vector: Optional[object] = None`
2. `src/graph_builder.py` — 新增 `compute_tfidf_index()` 方法
   - token = regex `[a-z]{3,}`，去掉 30 个常用停用词
   - IDF = log((N+1)/(df+1)) + 1（smoothed，恒正）
   - 每个 sentence 向量 L2 归一
   - 同时暴露 `self._tfidf_vocab` (word→col) 和 `self._tfidf_idf` (col→idf)
3. `src/stengraph_pipeline.py` — `_score_sentences` 优先调用新方法
   `_score_tfidf(query, sids)`：在 `graph._tfidf_vocab` 上建 query 向量，
   做 dense dot product (cosine 因为已 L2-norm)。缺 vocab/向量则
   优雅返回 None，调用方继续走 FAISS/Jaccard。
4. `eval/quick20_eval.py` — 在 `cm.update_container_index` 循环后
   调 `builder.compute_tfidf_index()`（必须在 dispatcher.run 之前）。

### 软备份策略
没生成 .bak 文件（之前 powershell Copy-Item 卡住 20 分钟），
改前我已读完所有改动区域的原代码；任何回滚只需 `StrReplace` 还原。

### 跑前
v4 (seed=1234) = EM 0.300 / R@1 0.250 / R@5 0.400

### 跑后 (3 seed 平均)
| seed | EM   | F1   | R@1  | R@5  | R@10 | lat(ms) |
|------|------|------|------|------|------|---------|
| 7    | 0.00 | 0.044| 0.20 | 0.45 | 0.45 | 1564    |
| 1234 | 0.00 | 0.045| 0.25 | 0.35 | 0.35 | 1682    |
| 2025 | 0.00 | 0.054| 0.25 | 0.50 | 0.50 | 1471    |
| **avg** | **0.00** | **0.048** | **0.233** | **0.433** | **0.433** | 1572 |

### 关键观察
1. **R@5/R@10 微涨** (+0.033/+0.033) — tfidf 召回确实更广，把更多
   gold 句子拉进 top-5。**检索端有正向信号**。
2. **R@1 几乎不变** (-0.017) — top-1 句子质量持平。
3. **EM/F1 暴跌 0.30→0.00** — *不是 tfidf 的锅*。看 `extract_answer_from_dispatch`
   走的是 `if client is None: return first line of final`。
   tfidf 改变了 top 句子顺序 → 拿到的第一行句子不同 → heuristic
   top-entity 抽到的实体不同 → EM 0。
4. **网络问题**：跑前发现 HuggingFace 不可达，`SentenceTransformer`
   构造会卡 20+ 分钟。已加 `_EMBEDDER_CACHE` 预填 None + 环境变量
   `HF_HUB_OFFLINE=1` 旁路。从平均 4-5s/题 降到 1.5s/题。

### 结论
- 改造 A **检索部分保留**（R@5 提升）。
- EM 暴跌根因是 answer extraction，不是 tfidf 本身差。需要在
  后面加一步 LLM answer span 提取（或改善 heuristic），不在本
  次改造范围。
- 下一站：超边 chunk_id 改造（用 paragraph title 而非 qid），
  跑 3 seed 对照。

## 改造 B: 属性表滚动优化 Agent（上下文记忆设计）

### 目的
上下文记忆设计阶段需要一个 **agent 滚动优化属性表**：随机抽 20 题
× 10 轮，让 agent 判断是否缺少对应属性、实体是否缺少对应的类；
如果缺少则补充。补充必须满足两条硬性要求：

1. **包容性** — 属性必须能容纳一类句子，不能是只对一句话成立的
   一次性细节；否则它会白白占掉属性向量矩阵的一个槽位。
2. **挂载效率** — 属性如果挂不到几个句子，就丢弃该属性或该类。

此外，挂载必须 **有区分度**：要能区分属性属于谁，
例如 `birth(A)`、`date(EVENT_A)`——属性挂在具体实体上，
而不是笼统地属于某个大类。如果一句话含多实体且同属一个大类，
则调用 LLM 判断兜底。

### 改动
1. **新增 `src/attribute_schema.py`** — 属性表的运行期增量层。
   - `AttributeSpec` / `ClassSpec` / `AttributeSchema`：agent 的增量
     （新属性 + 新实体类），可 apply / save / load / export。
   - `ATTRIBUTE_CANDIDATE_LEXICON`：**有界**候选属性表
     （nationality / religion / cause_of_death / also_known_as /
     military_service / language / area / climate / dissolved / cause）。
     agent 不得凭空发明无界的属性词表。
   - `CLASS_CANDIDATE_LEXICON`：候选实体类表
     （FAC / PRODUCT / LAW / LANGUAGE / TIME）。
   - `apply_to_modules()` 就地修改 `sentence_graph` 的三张表
     （`ATTRIBUTE_DESCRIPTORS` / `ATTRIBUTE_NAMES` /
     `_ATTRIBUTE_TEMPLATES`）。**必须就地改**：`graph_builder` 与
     `stengraph_pipeline` 在 import 时就按名字绑定了这些对象，
     重新绑定模块属性会让它们继续指向旧列表。
   - `apply_to_registry()`：patch 已建好的 `AttributeRegistry`
     （它的 `_templates.copy()` 是浅拷贝，新类必须显式写入）。

2. **新增 `src/attribute_agent.py`** — agent 本体，闭环为
   **采样 → 检测缺口 → 提议 → 三准则把关 → 应用 → 重新挂载**。
   - `AttributeAgentConfig`：可调参数（轮数、阈值、LLM 上限）。
   - `QUESTION_TRIGGERS`：问题侧触发词表。属性缺口是在 **问句**
     上检测的（"When was X born" 问的是 `birth`，句子里并不含
     "born"），与 `sentence_graph` 里的句级词干表是两套东西。
   - **缺口检测**：
     - *缺类* — 锚实体的 spaCy 类型没有自己的模板，
       只能挂 `description` 兜底，不携带任何信号；
     - *缺属性* — 问句要的属性不在该实体的类模板里，且不在候选
       词表内则不许提议。
   - **三准则把关**（`_gate`）：
     1. 包容性 — 触发词/词干太少、descriptor 与已有属性重复
        （cos ≥ 0.80）→ 丢弃；
     2. 挂载效率 — 挂载句数 < `min_mount_count` 或全库占比 <
        `min_global_mount_rate` → 丢弃；
     3. 区分度 — 该属性在本类的 top-K 命中率必须比其它 **可能拥有
        该属性的类** 高出 `min_distinctiveness_margin`，否则它不区分
        任何东西 → 丢弃。
   - **度量必须复刻真实挂载**（`_measure`）：排序集合是实体自己的
     模板（真实挂载只允许挂模板里声明的属性），且**先加权再排序**
     （`description` 兜底权重 0.7，不能占掉 top-K 槽位）。
   - **LLM 只在两处兜底**，且都可关闭：
     - 同大类多实体的归属（"Washington and Lincoln" 这句事实属于谁）；
     - 缺口确认（检测基于触发词，可能是假阳性）。
   - agent **不改源码**：增量落盘为 JSON，`export_python()` 可导出
     成可粘贴的源码片段，由人决定是否固化。

3. **`src/graph_builder.py`** — `GraphBuilder.__init__` 新增
   `attribute_schema` 参数，在第一个容器创建**之前** apply，
   这样新属性/新类进入它派发的每一个模板。

4. **新增 `eval/attribute_agent_eval.py`** — 驱动脚本（采样参数、
   增量落盘、报告输出）。`--schema` 可载入已有增量继续往前滚。

5. **新增 `eval/attribute_agent_selftest.py`** — 43 项确定性自测，
   不依赖 spaCy / embedder / LLM / 数据集，锁死三条把关准则。

6. **新增 `eval/attribute_agent_smoke.py`** — 合成语料端到端冒烟测试。

### 跑前
属性表为静态常量，无缺口检测能力。

### 跑后
合成语料冒烟（`eval/attribute_agent_smoke.py`，n=4×2 轮）：
- 检出缺口 3 个：`PERSON::religion`、`PERSON::nationality`、
  `FAC`（缺类）
- 通过 2 个：`religion`（判给 NORP，margin 0.650）、
  `FAC` 缺类（`location` / `events` / `function` 挂载效率达标）
- 丢弃 1 个：`nationality` 对 PERSON — NORP 的命中率更高
  （0.750 vs 0.300），margin 为负，属性区分不出 PERSON。

自测 43 项全通过（`eval/attribute_agent_selftest.py`，不依赖
spaCy / embedder / LLM / 数据集）。

> 真实指标（EM / F1 / R@k）需在 HotpotQA 上跑 `quick20_eval.py`
> 对照；数据集不在仓库内（`.gitignore` 排除 `eval/data/`）。

### 实现中踩到的三个坑（都写进了 DESIGN.md）

1. **度量必须复刻真实挂载**。用"该句与 descriptor 的余弦"直接
   判定会系统性高估——真实挂载受模板限制、且 `description` 被降权
   到 0.7，两处都会改变 top-K 归属。改法：排序集合取实体自己的
   模板，**先加权再排序**，只取 top-K。
2. **owner 类必须由度量决定，不能假设**。缺口是在问句锚点上检测的，
   但属性不一定归该类所有（`religion` 对 PERSON 和 NORP 一样合适）。
   改法：在候选类里比"赢下多少个 top-K 槽位"，赢最多的成为 owner；
   平票时问句锚点优先（否则会按字母序把 `religion` 判给 NORP，
   而问句问的其实是人）。
3. **句子 ID 会跨图重复**。每次建图都从 `s_0001` 开始，直接累加
   会把同一张图的统计数 200 遍，所有全库指标都会算错。
   改法：profile 用 `"{qid}::{sid}"` 加命名空间。

### 结论
- 属性表从"写死的常量"变成"可被 agent 读写的运行期 schema"，
  滚动优化不必改源码。
- 关键设计取舍：**度量必须复刻真实挂载**。用"该句与 descriptor
  的余弦"直接判定会系统性高估——真实挂载受模板限制、且
  `description` 被降权，两处都会改变 top-K 归属。

## 改造 B: attribute_agent 接入 quick20_eval（一体化跑批）

### 目的
原先 `attribute_agent_eval.py` 和 `quick20_eval.py` 是两个互不相干的
脚本：agent 只产出属性增量，quick20 只测 EM/F1。**增量对检索指标
到底有没有正收益，无人测过** —— 只能靠人肉把 JSON 灌回源码，
再跑一次 quick20 对比。

改造目标：一条命令同时完成「滚动优化 → 应用增量 → 测 EM/F1」，
并且支持 **A/B**（同一份样本，增量前跑一次、增量后跑一次），
让属性的收益/代价可以直接量化。

### 改动
1. **`eval/attribute_agent_eval.py`** — 抽出可复用入口
   - `run_attribute_agent(questions, *, ...) -> AgentReport`：
     原来的 `main()` 逻辑整体下沉到这个函数，负责采样参数、
     构造 `AttributeAgentConfig`、跑 `agent.run()`、落盘
     report / schema / snippet。
   - `log_report(report)`：把原先散在 `main()` 里的报告打印
     抽成独立函数，供 quick20 直接复用。
   - 新增 `nlp` 入参：复用 quick20 已经加载好的
     `en_core_web_lg`，避免第二次加载 spaCy 模型。
   - `main()` 改为薄封装，只负责 argparse + 调 `run_attribute_agent`。
   - `run_attribute_agent` 的 `questions` 同时接受
     「原始 HotpotQA 记录」和「`load_questions()` 之后的 dict」，
     后者按 `qid` 键自动识别（quick20 传的是原始记录）。

2. **`eval/quick20_eval.py`** — 接入点
   - 新增 CLI：
     - `--attr-agent` —— 先跑 agent 并应用增量，再评测。
     - `--attr-agent-ab` —— A/B 模式：增量前跑一次（baseline），
       agent 跑完应用增量后再跑一次（treatment），最后打印
       EM/F1/R@k 的逐项差值。隐含 `--attr-agent`。
     - `--attr-agent-n` / `--attr-agent-rounds` /
       `--attr-agent-seed` —— agent 的采样参数（默认 20×10，seed 1234）。
     - `--attr-agent-schema` —— 从已有增量继续往前滚。
     - `--attr-agent-out` / `--attr-agent-report` —— 落盘路径。
     - `--attr-agent-no-llm` —— 关掉 agent 的 LLM 兜底。
     - `--attr-agent-dry-run` —— 只报缺口，不应用增量。
   - 把原本内联在 `main()` 里的评测循环抽成
     `_evaluate_sample(args, sample, nlp, client, offline_store)
     -> (summary, records)`。**关键点**：容器派发属性槽位时读的是
     `src.sentence_graph` 的模块级模板，所以"当前生效的属性表"
     就是 A/B 两次之间唯一变化的变量 —— baseline 在 agent 应用增量
     **之前**跑，treatment 在之后跑。
   - A/B 差值打印（`_log_ab_delta`）+ 落盘 `<out>_ab.json`，
     内含 baseline / treatment / delta 三段，以及 agent 侧的
     缺口数、接受数、接受的属性名与类名。
   - 主结果 JSON 增加 `attr_agent` 段，记录本次是否跑了 agent。

### 跑前
属性 agent 与 quick20 脱节，增量对 EM/F1 的影响**无数据**。

### 跑后
待跑（见下方"终端命令"）。

### 结论
- agent 的产出从"一个孤立的 JSON"变成"可被评测闭环验证的增量"。
- A/B 顺序是硬约束：baseline 必须在 agent 应用增量之前跑，
  否则两侧都用新表，delta 恒为 0。
- 改动时间：2026-10-29
- 改动目的：把属性滚动优化接进 quick20 评测闭环，使其可被指标验证
- 改动功能：新增 `--attr-agent` / `--attr-agent-ab` 等 10 个参数，
  抽出 `_evaluate_sample()` 与 `run_attribute_agent()` 两个可复用入口

## 改造 C: LLM 配置接入 llm_client（.env 自动加载）

### 目的
`src/llm_client.py` 的 `make_client()` 只读 `os.environ`，**从不加载
仓库根目录的 `.env`**。README 里让用户手动 `load_dotenv()`，但仓库里
没有任何脚本这么做。后果是：

- `make_client()` 返回一个 **disabled** 的 client；
- 所有依赖 LLM 的功能（实体抽取、答案抽取、agent 的缺口确认）静默降级
  成启发式回退；
- **日志上看不出来** —— client 是 disabled 而不是报错。

这直接毁掉上一条改造（B）的 A/B 测量：treatment 和 baseline 都没真正
用上 LLM，两边必然一模一样，delta 恒为 0。

### 改动
1. **`src/llm_client.py`**
   - 新增 `load_env_file(path=None)`：读 `.env` 并写入 `os.environ`，
     **不覆盖**已存在的变量（真实环境变量永远优先）。
   - 新增 `_parse_dotenv(text)`：内置的极简解析器（`KEY=value`、
     `export KEY=value`、引号剥离、行尾注释）。`python-dotenv` 装了
     就用，没装就用这个 —— 遵守"不引入新重型依赖"的项目规则，同时
     避免"可选依赖缺失 = 功能缺失"。
   - 新增 `_ensure_env_loaded()`：每进程只加载一次。
   - `make_client()` 与 `DeepSeekClient.__init__` 都调用它。
   - 新增三个自省接口：
     - `llm_available()` —— 有 key 或配了本地服务器 → True；
     - `local_llm_configured()` —— 是否指向本地 vLLM；
     - `describe_llm_config()` —— **脱敏**的一行配置摘要
       （端点 / 模型 / 有无 key，绝不输出 key 本身）。
2. **`eval/quick20_eval.py`** / **`eval/attribute_agent_eval.py`** —
   启动时打印 `LLM config: ...`，让"这次跑到底有没有用上 LLM"写在
   日志里。
3. **`.env`** — 新建（已 gitignore），带中文注释说明两种配置方式。
4. **`.env.example`** — 补齐本地 vLLM 的三个变量。
5. **`requirements.txt`** — 把 `python-dotenv` 标为 optional。

### 跑前
`make_client()` 读不到 `.env` → client disabled → LLM 路径静默失效。

### 跑后
- `.env` 存在 → `make_client().enabled == True`，key 正确解析。
- 优先级验证：进程环境变量 > `.env`（已测）。
- 本地 vLLM 路径：`STENRAG_LLM_BASE_URL` 一设 → 走本地 + 占位 key
  （已测）。
- 真实调用打到 DeepSeek 并返回 **401**（key 还是占位符 `sk-your-...`
  未替换），说明请求链路本身是通的；401 被 `answer_extractor` 捕获后
  返回 `""`，优雅降级不崩。

### 结论
- "LLM 有没有真的在用"必须是**日志里看得见**的量，否则 A/B 数字不可信。
- 可选依赖不能悄悄变成功能缺失 —— 故内置 fallback 解析器。

> 下一步（等用户指令）：把真 key 填进 `.env`，然后跑
> `python eval/quick20_eval.py --n 20 --seed 7 --attr-agent-ab`。

## 改造 D: 属性表可增可减 —— 剪枝（prune）通道

### 目的
原始需求写的是 *"如果这个属性后面挂载句子效率低就丢弃这个属性或者类"*，
但 agent 原本**只增不删**。后果是属性表单调增长：

- 一个挂载效率早已崩溃的属性，会一直占着 attribute embedding 矩阵的
  一个槽位 —— 而这个槽位是**每个实体模板都要付**的；
- 一个已经没有任何句子能挂上去的实体类，会一直占着模板槽位，该类的
  每句话都只能落到 `description` 兜底里；
- 于是"滚动优化"名不副实 —— 它只涨不跌。

另外 `log_table_diff()` 的 REMOVED 段落当时写死成
`"(none — the agent only adds; it never deletes a table entry)"`，
永远不可能有内容。

### 改动
1. **`src/attribute_schema.py`** —— 删除通道
   - 新增 `remove_attribute()` / `remove_class()` / `is_removed()` /
     `is_class_removed()`；
   - 删除以**墓碑**（`removed_attributes` / `removed_classes`）记录而
     不是 `del`：delta 要存 JSON 再加载，墓碑能扛过这一轮，`del` 不能
     —— `sentence_graph` 的基础表会把被删条目复活；
   - `effective_templates()` 在"基础表 + 增量"合并**之后**统一套用
     墓碑，所以墓碑也能删掉基础表声明的属性；
   - `apply_to_modules()` 真正把条目从 `ATTRIBUTE_DESCRIPTORS` /
     `ATTRIBUTE_NAMES` / `_ATTRIBUTE_STEMS` / `_ATTRIBUTE_PATTERNS` /
     `_ATTRIBUTE_TEMPLATES` 中 pop 掉；
   - `apply_to_registry()` 让在线 registry 也停止挂载它；
   - `to_dict()` / `from_dict()` 持久化墓碑，`export_python()` 导出
     删除片段；
   - 新增 `copy()`（剪枝跑在工作副本上，dry run 不污染 live delta）；
   - **删类连带删属性**：一个类被剪掉时，只有它声明的属性一起剪掉

## 改造 F: 精排公式修复（量纲归一化 + 词法信号接回 + 属性门保底）

### 目的

用户实测（带 `--attr-soft-match`）得到一个很有信息量的**组合症状**：

| 指标 | 方向 |
|---|---|
| R@1 / R@5 / R@10 | **全部上升** |
| EM / F1 | **下降** |

这个组合本身就是诊断结论：**属性表在召回层是有效的，问题出在排序层。**
属性把对的句子带进了候选池，却没能把它排到第一。

用户明确指示走"路线 B"：修 rerank 的流程与公式。

### 改动

#### F1. 精排公式改为「先归一化、再加权」（D34）

**问题**：`src/stengraph_pipeline.py::_event_fact_score` 旧公式把不同
量纲的余弦直接相加：

```python
final = W_EVENT * (W_EVENT_NAME * cos(title,q) * pen
                   + W_EVENT_SENT * cos(sent,q))
      + (1 - W_EVENT) * cos(sent,q)
      + W_ATTR * attr - echo_pen
```

实测典型值：`cos(title,q) ∈ [0.15,0.35]`，`cos(sent,q) ∈ [0.35,0.55]`。
直接相加时**方差大的分量主导** —— 名义上"事件名主导"
（`W_EVENT_NAME=0.7`）的实现里，实际主导的是句子向量。

同理 `W_ATTR=0.10` → `attr_term ∈ [0,0.10]`，而 final 的动态范围约
0.2–0.6：属性的整个取值范围只相当于句子余弦波动的 1/4，属性表的
所有改进在最终排序里几乎不可见。

**改动**：新增模块级 `_minmax_norm(values)`，把每个分量在候选池内
min-max 归一化到 [0,1] 后再加权：

```python
final = W_EVENT_NAME_N * norm(cos(title,q) * pen)
      + W_SENT_N       * norm(cos(sent,q))
      + W_FACT_N       * norm(entity_coverage)
      + W_ATTR         * norm(attr_match)
      + W_LEX          * norm(bm25 ⊕ shape ⊕ relation)
      - echo_pen
```

归一化是单调变换，不改变单个分量内部的排序，只改变分量之间的相对
影响力 —— 这正是需要修的东西。归一化后权重才真正等于"这个分量占
最终分数的几成"。

退化情形（所有候选该分量相同）返回全体 1.0，避免所有候选塌成 0.0
而丢失判别力。

#### F2. 事实项换成「问句实体覆盖度」（D35）

**问题**：旧 `fact_term = (1-W_EVENT) * sh_f`，而 `sh_f` 就是
`sent_term` —— **同一个余弦被用了两次**。整条公式退化成
"句子余弦 × 常数"，name / attr / lex 的相对权重被进一步稀释。

**改动**：新的事实项是问句实体锚点的覆盖度：候选句覆盖了问句里多少
个实体（分组匹配，命中整名或末词形态都算覆盖该实体）。HotpotQA 是
多跳题，答案句往往同时提到问句里的两个实体；只提到一个的句子不可能
独立回答这个问题。这个信号与句法关系（看动词）正交，也与句向量余弦
正交。

#### F3. 词法信号接回打分链路（D36）

**问题**：三个本该参与打分的信号全是**死代码**：

- `_score_tfidf`（BM25）—— Step 7 被删后失去唯一调用者；
- `_answer_shape_features`（答案形状先验）—— 同样失去调用者；
- `_last_query_relations`（问句句法骨架）—— 抽出来存进去之后
  从未被任何打分环节消费。

也就是说排序只剩两个稠密余弦，而 BM25 的 IDF 实体区分度、专门为
HotpotQA 写的答案形状先验、问句的动词/宾语句法锚点，**全部不参与
打分**。

**改动**：新增 `W_LEX`（默认 0.30），把三个信号归一化后融合：

| 子信号 | 内部权重 | 说明 |
|---|---|---|
| BM25 | 0.50 | 靠 IDF 救回稀有实体（Havel / Fitzgerald 这类词在稠密余弦里被稀释） |
| 答案形状先验 | 0.25 | 问 `when/what year/how many/how much/how long/how old` → 期望答案含数字；否则期望专名密度高 |
| 句法关系匹配 | 0.25 | 问句的 verb/obj 词干 vs 候选句 token；verb 权重更高（0.6/0.4），因为动词才区分"是不是在回答这个问题" |

融合后再整体归一化一次，避免融合值超出 [0,1] 破坏 `W_LEX` 语义。

BM25 不可用（没有 TF-IDF 词表）时，形状先验**单独**生效 —— 不能
因为词法链路的另一半断了就把这一半也丢掉。

#### F4. 属性硬门设保底下限（D37）

**问题**：旧逻辑**只有在门把池子清空时**才放宽。一个"30 个候选只留
1 个"的门也被当作"正常工作"。

**这正是"recall 涨、EM 跌"的直接机制**：属性门决定**候选资格**，一个
校准不准的 wanted-attribute 集合会在排序器看到 gold 句**之前**就把它
删掉。活下来的句子都 on-topic（recall 上升），但带着答案的那句没了
（EM 下降）。

**改动**：

```python
floor = max(1, min(ATTR_GATE_MIN_KEEP, top_k))   # ATTR_GATE_MIN_KEEP = 3
for level in (3, 5, 8):
    passed = [...]  # mounted_attrs ∩ wanted_attrs[:level] ≠ ∅
    if len(passed) >= floor:
        kept = passed; gate_level = level; break
else:
    kept = top-N by final_score   # N = max(floor, ATTR_GATE_MIN_KEEP)
```

放宽层级记在 `attr_gate_level`，校准不准时在日志里看得见。

#### F5. 属性 coverage 的符号修正（D38）

**问题**：`coverage = Σc_k / count`（平均值）的**符号是反的** ——
挂载的属性越多，平均值反而被拉低，"对齐度"反而变差。

**改动**：`coverage = Σc_k / max_k c_k ∈ [0,1]`，含义是"有多少信号
集中在最好的那个属性上"。挂载多个且一致的属性会**提高**它。

#### F6. 顺带修的性能问题

旧代码在内层循环里对每个属性做一次 `ATTRIBUTE_NAMES.index(...)` ——
40+ 个属性 × 数百个句子 = 每题几万次线性扫描。改成预建
`attr_index` 字典。

#### F7. 诊断字段与日志改名

每行结果同时保留**归一化后**的分量（`norm_name` / `norm_sent` /
`norm_fact` / `norm_attr` / `norm_lex`）和**原始**余弦
（`raw_name_cos` / `raw_sent_cos`）—— 权重乘的是归一化值，两个都留
才能在事后定位权重回归。

`[EF-rank]` 日志原来打印 `W_EVENT` 和 `avg_(1-wE)·S_h_F`，描述的是
旧公式。改成逐个列出五个新分量的权重与平均贡献 —— **打错名字的日志
比没有日志更糟**，因为它会自信地报错排序行为。

### 跑前

用户的实测（带 `--attr-soft-match`，用户自己跑的）：

> recall 均获得了提升，证明在召回层属性的价值是有的，而 EM/F1 却降低，
> 我认为是重排序等问题导致的。

### 跑后

待跑（见下方"终端命令"）。

### 结论

- **recall↑ + EM↓ 是个非常有用的信号**：它把问题精确定位在排序层，
  而不是属性表本身。属性表该保留，该修的是它下游的排序。
- 排序公式里**量纲不可比**是一个静默的 bug：权重写得再漂亮也不生效，
  因为方差大的分量会无视权重自己主导。
- 硬门的"删除"语义比它的"过滤"语义危险得多 —— 它在排序之前就剥夺
  了候选资格，所以**必须有保底下限**。
- 死代码不会自己报警。`_score_tfidf` / `_answer_shape_features` /
  `_last_query_relations` 三个信号都曾经被正确地实现过，只是调用者
  被删掉之后就再也没人用了。

## 改造 G: R@k 的 gold 判定修复（子串 bug）

### 目的

用户要求修复 recall 的子串 bug。这是上一轮分析中**唯一一个确定可修**
的指标错误。

### 问题

R@k 的旧判定：

```python
gold_norm in _normalize_answer(node.text or "")
```

**子串包含**，在两个方向上都是错的：

**(a) 假阴性 —— 系统性低估 recall。**
gold 是 `'yes'`（HotpotQA 的 "same X?" 类问题）时，整个 context 里
**没有任何一句包含 "yes" 这个子串**。这类题的 R@k **恒为 0**，无论
检索质量多好。

在 seed=7 的 20 题里就有 1 题（Q4，gold=`'yes'`）属于这种情况 ——
也就是说上一轮报的 **R@10=0.800 里有一半是量纲错误**，真实上限是
17/20 = 0.850。

300 题抽样上，这类题占 **2.3%**。它们系统性地压低 recall，且压低
幅度**与检索质量无关** —— 也就是纯噪声，会让 A/B 对比失去意义。

**(b) 假阳性 —— 判定过松。**
gold 是 `'Matthew Good'` 时，`'matthew good'` 是
`"…on Matthew Good's own imprint…"` 的子串 —— 但那一句讲的是唱片的
发行，不是答案句。

300 题抽样里，**25.7%** 的题会匹配到 ≥3 个句子。

### 改动

1. **`eval/recall_utils.py`（新建）** —— R@k gold 判定的**唯一真相源**
   - 主判据：数据集自带的 `supporting_facts` 标注（`[[title, sent_idx]]`
     或 `[{title, sentence_id}]`）→ 解析成图里的句子 ID。**权威**。
   - 降级判据：词边界答案包含 `(?<!\w)gold(?!\w)`，消除假阳性。
   - 极性题（gold 是 `yes`/`no`）标记为**不可评分**，排除出 R@k 分母。
   - `GoldMatcher` 记录 `match_kind` / `reason`，随指标落盘。
2. **`eval/quick20_eval.py`** —— 三处改动
   - 主评估路径：改用 `gold_sentence_matcher`；极性题不计入
     `r1s/r5s/r10s`（分母因此正确）；新增 `r_scorable` / `r_polar` /
     `r_match_kinds` 计数与日志行
     `Recall denominator: N scorable / M total (K polar excluded, {...})`。
   - `summary` 新增 `recall_denominator` 字段（**分母必须随指标落盘**，
     否则跨运行的 R@k 数字不可比）。
   - DIAG 块里那份**重复的 `supporting_facts` 解析**改为复用共享实现
     （删掉 48 行重复代码）。
   - `hyperedge_compare` 路径：极性题记 `-1` 哨兵，`_m()` 改为只对
     可评分项求平均；日志显示 `n/a` 而不是误导性的 `-1`。
3. **`eval/quick20_clean.py`** —— 同样改用共享实现。

### 为什么极性题是排除而不是记 0

`yes`/`no` **不是句子片段**，没有任何句子能"包含"它。所以：

- 记 0 → 系统性压低均值，且压低幅度取决于样本里恰好有多少极性题；
- 记 1 → 虚高（等于"排第一就得分"，与检索无关）；
- **排除 + 报数** → 唯一诚实的做法。

日志会明确打出 `[RECALL-SKIP] <qid> polar gold='yes' — excluded from
R@k`，不会静默地稀释均值。

### 量化价值

seed=7，20 题，假设**检索完美、gold 支撑句排第一**：

| 指标 | 旧判定 | 新判定 |
|---|---|---|
| R@1 上限 | **0.650** | **1.000** |
| R@5 上限 | **0.950** | **1.000** |
| R@10 上限 | **0.950** | **1.000** |

旧指标**即使检索完美也无法报告 R@1 = 1.0** —— 它测的不是检索质量，
而是"答案串恰好落在哪个句子"。

seed=7 每题的判定变化（旧命中数 → 新命中数）：

| 题 | 类型 | 旧命中 | 新命中 | 说明 |
|---|---|---|---|---|
| Q3 | comparison | 13 | **4** | 假阳性大幅清除（`'Matthew Good's'`） |
| Q5 | comparison | 6 | **3** | 同上 |
| Q4 | comparison | 0 | 0 | 极性题 → 排除出分母 |

### 跑后

修复后的实测（n=5, seed=7, 无 LLM，冒烟）：

```
n=5  EM=0.800  F1=0.800  R@1=0.500  R@5=0.750  R@10=0.750
Recall denominator: 4 scorable / 5 total (1 polar excluded, {'supporting_facts': 4})
```

R@1 = 2/4（分母 4，不是 5）✓

### 结论

- **指标错误比模型错误更危险**：模型错误会体现在 EM 上，指标错误
  体现在"所有方案都被压低"，让 A/B 对比变成噪声。
- **子串匹配看起来最自然，实际上是错的**：它把"gold 答案串出现
  在句子里"当成了"这句是答案句"，而 HotpotQA 的 gold 支撑句是
  标注出来的，不是反推出来的。
- **同一规则的四份实现是漂移的根源**：`quick20_eval.py` 里 DIAG 块
  那份 `supporting_facts` 解析和 R@k 那份几乎一样但独立演化。修
  R@k 的时候如果不动它，诊断数据和指标就会开始互相矛盾。

## 改造 H: 硬属性门 → 软门 + 槽位匹配 + 保底保证

### 起因

改造 G 修好 R@k 指标后，第一次拿到了**可信的**属性 A/B 数据
（seed=7 / 20 题，DeepSeek）：

| | 无属性 | 有属性 | Δ |
|---|---|---|---|
| EM | 0.850 | 0.750 | **-0.100** |
| F1 | 0.850 | 0.750 | -0.100 |
| R@1 | 0.684 | 0.579 | -0.105 |
| R@5 | 0.842 | 0.789 | -0.053 |
| R@10 | 0.947 | 0.789 | -0.158 |

结论：**属性在召回层的价值是有的，但精排把它用坏了。**

### 根因定位

RANK-DIAG 的两个数字直接指出了病灶：

```
[RANK-DIAG] n=20 | 召回丢失=0  门删掉=0→5  排序丢失=6→2
```

**排序反而变好了**（排序丢失 6 → 2，gold 排第 1 的 14 → 13 基本持平），
恶化 100% 来自"门删掉"这一项（0 → 5）。

逐题复盘那 5 道被门删掉 gold 的题，**两道的 gold 的 `final_score` 是
全场第 1**：

| 题 | gold | gold final_score | 门删掉前排名 | EM |
|---|---|---|---|---|
| 5ab9d2e2 | `102,984` | **0.962** | **第 1** | ✗ |
| 5a74cfed | `Matthew Good` | **1.072** | **第 1** | ✓ |
| 5abe689a | `French Open` | 0.645 | 第 12 / 24 | ✓ |
| 5a9094ba | `Richard Gerald "Dick" Purcell Jr.` | 0.651 | 第 13 | ✓ |
| 5abaad58 | `three singles titles` | 0.343 | 第 21 | ✗ |

**排序器判断正确，门把它删掉了。** 门的删除行为覆盖了排序器的判断。

再看 wanted 与 mounted 的重叠：

| 题 | gold 挂载的属性 | 门想要的 | 重叠 |
|---|---|---|---|
| 5ab9d2e2 | `achievement, career, education, event` | `location, population, residence` | **0** |
| 5a74cfed | `beliefs, events, founded, headquarters, history, location, members, origin`（8 个） | `birth, career, education` | **0** |
| 5a9094ba | `birth, career, education, leadership, origin` | `characters` | **0** |
| 5abe689a | `event, origin` | `achievement` | **0** |
| 5abaad58 | `[]`（无挂载） | `achievement` | **0** |

**5 道题全部零交集。**

根因：`wanted_attrs` 只取 query 侧 embedding 余弦的 top-3，
**完全不看 sentence 侧挂了什么**；而 `mounted_attrs` 是"实体类型 ×
属性类别"的粗分类。两边都是粗的 → 经常零交集 → 门误杀。

这是**粒度问题，不是阈值问题** —— 调大调小 `ATTR_GATE_TOP_K`、
调 `ATTR_GATE_MIN_KEEP` 都治不了"wanted 集合本身是错的"。

### 三项改动

#### 改动 1：硬门 → 软门（D40）

属性**不再有删除权**，保留为打分分量（`W_ATTR`）。不满足的句子只是
拿不到属性加权、排序时自然下沉。

> 属性从"准入证"退回"加分项" —— 这才是排序信号应有的位置。

门仍然**观测**并记录"如果这是硬门会删掉多少"，让误校准的属性表保持
可见：

```
[EF-attr-gate] SOFT gate — 17/25 candidates carry none of the wanted
attrs ['birth', 'career', 'education'] (kept anyway; attr is a ranking
signal, not an admission ticket)
```

`attr_gate_kept` / `attr_gate_pass` 字段语义变了（恒为 True），但
**接口不变** —— eval 的 RANK-DIAG 仍能读旧的结果文件。

#### 改动 2：实体-属性槽位匹配（D41）

粗粒度问的是"这个句子挂的属性 ∩ 问句想要的属性"；细粒度问的是
"**这个句子的这个实体**，是不是恰好挂着**问句想要的属性**"。后者才
是原始设计里 `birth(A)` / `date(EVENT_A)` 的粒度。

新增 `_entity_keys(name)`：返回实体的**三套索引键** ——
小写表面形式、去重音形式、末词降级形式。末词降级是因为 HotpotQA
问句常只写姓氏：

```
问句: "Which city was Havel born in?"
句子: "Václav Havel was born in Mělník ..."
```

`_entity_keys('Václav Havel')` → `['václav havel', 'vaclav havel', 'havel']`
→ 两边通过 `'havel'` 对上。

槽位分以**加成项**的形式进入 `attr_match`：

```
attr_match = max(粗粒度 attr_match, slot_bonus · ATTR_SLOT_MATCH_WEIGHT)
```

末词降级有误匹配风险（"John Smith" / "James Smith" 都降级到 "smith"），
所以槽位分**只提升分数、不参与删除**，`ATTR_SLOT_MATCH_WEIGHT` 默认
1.0 但留了余量让粗粒度信号在误匹配时把分数拉回来。

#### 改动 3：保底保证（D42）

**旧保底保护的是"数量"，不是"质量"。** `ATTR_GATE_MIN_KEEP=3` 只在
"池子被掏空"时触发，但误校准时池子往往还有 20+ 候选，门从容删掉
5 个 gold，保底根本不启动。

新保底保护的是"**排序器的判断**"：分数最高的 N 句（默认 = `top_k`，
由 `ATTR_TOP_SCORE_GUARANTEE` 控制）一定进入 LLM 上下文，任何后续
筛选都不能踢掉它们。

这是**最后一道防线**，独立于属性逻辑 —— 未来即使再加别的过滤器，
也绕不过它。代码里有显式断言，违反会打：

```
[EF-guarantee] VIOLATION: top-16 by score not all in final_rows — a
filter is running after the sort
```

### 跑后

冒烟（n=5, seed=7, `--attr-soft-match`）：

```
[EF-attr-gate] SOFT gate — 17/25 candidates carry none of the wanted attrs ... (kept anyway)
[EF-rank] kept 25/25 (soft gate deleted 0) → final 16/16 (top-16 score guarantee held)
n=5  EM=0.600  F1=0.600  R@1=0.500  R@5=0.750  R@10=0.750
Recall denominator: 4 scorable / 5 total (1 polar excluded, {'supporting_facts': 4})
```

无 `[EF-guarantee] VIOLATION`。

### 结论

- **门比信号更危险**：一个"看起来在提升精度"的硬过滤器，如果它的
  判定规则有系统性缺陷，就会**覆盖**掉整个排序器的判断 —— 而排序器
  的判断（实测两道的 gold 是全场第 1）本来是对的。
- **粒度问题不能靠阈值解决**：wanted 与 mounted 零交集是分类粒度
  太粗导致的，调 `ATTR_GATE_TOP_K` 只会在"删太多"和"删太少"之间
  摆动，不会让它们对上。
- **保底要保护判断，不是保护数量**。"上下文至少有 3 句"听起来像
  安全网，但真正需要保证的是"排序器认为最好的那几句"。

### 待验证

需要在完整 20 题上跑 A/B 确认：

```powershell

```

预期：EM 回到 0.850 附近（因为排序器本来就把 gold 排第 1），
且 `门删掉` 应恒为 0。

## 改造 I: 段落级指标（Passage Recall@k / Hit@k）

### 目的

用户指出：多跳检索论文（MDR、GraphRAG、LongRAG、FAIR-RAG 等）用的
recall 是**段落粒度**的，而现在报的是**句子粒度**。为了让本项目的
数字能与这些论文对齐，补上两个标准口径。

### 两个口径

**口径 A —— Passage Recall@k**（MDR / Xiong 2020）

\[
\text{Recall@k} = \frac{1}{|Q|}\sum_{q}\frac{|\text{top-k} \cap \text{gold passages}_q|}{|\text{gold passages}_q|}
\]

允许只抓到一半证据就得分 —— top5 里抓到 2 个 gold 段落中的 1 个 →
该样本贡献 0.5。

**口径 B —— Hit@k / Pair Recall@k**（GraphRAG / LongRAG）

\[
\text{Recall@k} = \frac{|\{q : \text{top-k} \supseteq \text{gold passages}_q\}|}{|Q|}
\]

必须**全部** gold 段落都在 top-k 里才算成功，缺任意一个直接 0。
适合多跳 RAG —— 少任意一篇证据就无法完成推理。

HotpotQA 每题恰好 2 个 gold 段落（已在 seed=7 的 20 题上核实），
所以口径 A ∈ {0, 0.5, 1}，口径 B ∈ {0, 1}。

### 改动

**`eval/recall_utils.py`**

- `build_sentence_to_paragraph(qdata, builder)` —— 句子 ID → 段落标题
  （小写）。图自己分配句子 ID，所以桥是**句子文本**。
- `gold_passage_titles(qdata)` —— 从 `supporting_facts` 取去重后的
  段落标题。HotpotQA 的 `supporting_facts` 是 `[[title, sent_idx], ...]`，
  **title 就是 gold 段落**，索引指向段落里的支撑句。
- `passage_metrics(ranked_sids, sent_to_para, gold_paras, ks)` ——
  同时算两个口径。

**排序转换规则**：两个指标都在段落粒度上定义，需要把"句子排序"
转成"段落排序"。规则是 **段落的位次 = 该段落里排名最高的那个句子的
位次**（first-appearance）—— 一个段落只要有任一句进了 top-k，它就算
被命中。

例：句子顺序 `[s_A1, s_B1, s_A2]` → 段落 A 位次 1，段落 B 位次 2。
top-2 里两个都在 → Hit@2 = 1。

**`eval/quick20_eval.py`**

- 主循环计算 `pmetrics`，累加进 `passage_acc`。
- 汇总日志新增段落级表格：
  ```
  Passage-level (n=5 queries):
    metric                             @1       @5      @10
    Passage Recall@k (口径A)        0.400    0.900    1.000
    Hit@k (口径B)                  0.000    0.800    1.000
  ```
- 每题日志行新增 `passage: PR@5=... Hit@5=... (gold paras=2)`。
- summary JSON 新增 `passage` 段（`n_scorable` + 两个口径的 @1/@5/@10），
  每条 record 新增 `passage` 字段。

**极性题不排除**：段落级指标和答案是 yes/no 无关，它只看证据段落
有没有被捞到。所以口径 A/B 的分母是**全部题数**，与句子级 R@k 的
分母（排除极性题）不同 —— **两者不可混用**。

### 单元验证

`passage_metrics` 的三个场景全部与手算一致：

| 场景 | @1 | @3 | @5 |
|---|---|---|---|
| alpha@0, gamma@1, beta@2 | PR=0.50 Hit=0 | PR=1.00 Hit=1 | PR=1.00 Hit=1 |
| 两个 gold 都在最前 | PR=0.50 Hit=0 | PR=1.00 Hit=1 | — |
| 只召回到 1 个 gold | — | PR=0.50 Hit=0 | — |

### 跑后（n=5, seed=7, `--attr-soft-match`）

```
Passage-level (n=5 queries):
  metric                             @1       @5      @10
  Passage Recall@k (口径A)        0.400    0.900    1.000
  Hit@k (口径B)                  0.000    0.800    1.000
```

### 结论

- **Passage Recall@10 = 1.000 而 EM = 0.750** —— 这是迄今为止最
  干净的证据：**检索层已经饱和了**，两个 gold 段落 100% 被召回，
  但答案仍然错。瓶颈在答案抽取，不在检索。
- 段落级指标比句子级**更能反映多跳检索的真实水平**。句子级
  R@10=0.789 看着像"还差 21%"，但段落级看是 **100%** —— 差别在于
  句子级要求"精确命中某一句"，而多跳 QA 真正需要的是"两个证据
  段落都在上下文里"。
- 两种口径必须都报：口径 A 宽容（允许半对），口径 B 严格（必须全
  对）。只看一个都会得出偏差的结论。
