## 改造 A: 句子级 TF-IDF 替换 Jaccard

### 目的
`StenGraphPipeline._score_sentences` 在没有 sentence-level FAISS
时回退到 token Jaccard。Jaccard 对"短、稀有的关键实体"（人名/地名）
不友好——比如 query "Who created the show that featured Triumph
the Insult Comic Dog?" 里的 "Triumph"/"Insult" 在 Jaccard 里权重
和 "the" 一样低。

### 改动
1. `src/sentence_graph.py` — `SentenceNode` 加 `tfidf_vector: Optional[object] = None`
2. `src/graph_builder.py` — 新增 `compute_tfidf_index()` 方法
   - token = regex `[a-z]{3,}`，去掉 30 个常用停用词
   - IDF = log((N+1)/(df+1)) + 1（smoothed，恒正）
   - 每个 sentence 向量 L2 归一
   - 同时暴露 `self._tfidf_vocab` (word→col) 和 `self._tfidf_idf` (col→idf)
3. `src/stengraph_pipeline.py` — `_score_sentences` 优先调用新方法
   `_score_tfidf(query, sids)`：在 `graph._tfidf_vocab` 上建 query 向量，
   做 dense dot product (cosine 因为已 L2-norm)。缺 vocab/向量则
   优雅返回 None，调用方继续走 FAISS/Jaccard。
4. `eval/quick20_eval.py` — 在 `cm.update_container_index` 循环后
   调 `builder.compute_tfidf_index()`（必须在 dispatcher.run 之前）。

### 软备份策略
没生成 .bak 文件（之前 powershell Copy-Item 卡住 20 分钟），
改前我已读完所有改动区域的原代码；任何回滚只需 `StrReplace` 还原。

### 跑前
v4 (seed=1234) = EM 0.300 / R@1 0.250 / R@5 0.400

### 跑后 (3 seed 平均)
| seed | EM   | F1   | R@1  | R@5  | R@10 | lat(ms) |
|------|------|------|------|------|------|---------|
| 7    | 0.00 | 0.044| 0.20 | 0.45 | 0.45 | 1564    |
| 1234 | 0.00 | 0.045| 0.25 | 0.35 | 0.35 | 1682    |
| 2025 | 0.00 | 0.054| 0.25 | 0.50 | 0.50 | 1471    |
| **avg** | **0.00** | **0.048** | **0.233** | **0.433** | **0.433** | 1572 |

### 关键观察
1. **R@5/R@10 微涨** (+0.033/+0.033) — tfidf 召回确实更广，把更多
   gold 句子拉进 top-5。**检索端有正向信号**。
2. **R@1 几乎不变** (-0.017) — top-1 句子质量持平。
3. **EM/F1 暴跌 0.30→0.00** — *不是 tfidf 的锅*。看 `extract_answer_from_dispatch`
   走的是 `if client is None: return first line of final`。
   tfidf 改变了 top 句子顺序 → 拿到的第一行句子不同 → heuristic
   top-entity 抽到的实体不同 → EM 0。
4. **网络问题**：跑前发现 HuggingFace 不可达，`SentenceTransformer`
   构造会卡 20+ 分钟。已加 `_EMBEDDER_CACHE` 预填 None + 环境变量
   `HF_HUB_OFFLINE=1` 旁路。从平均 4-5s/题 降到 1.5s/题。

### 结论
- 改造 A **检索部分保留**（R@5 提升）。
- EM 暴跌根因是 answer extraction，不是 tfidf 本身差。需要在
  后面加一步 LLM answer span 提取（或改善 heuristic），不在本
  次改造范围。
- 下一站：超边 chunk_id 改造（用 paragraph title 而非 qid），
  跑 3 seed 对照。

## 改造 B: 属性表滚动优化 Agent（上下文记忆设计）

### 目的
上下文记忆设计阶段需要一个 **agent 滚动优化属性表**：随机抽 20 题
× 10 轮，让 agent 判断是否缺少对应属性、实体是否缺少对应的类；
如果缺少则补充。补充必须满足两条硬性要求：

1. **包容性** — 属性必须能容纳一类句子，不能是只对一句话成立的
   一次性细节；否则它会白白占掉属性向量矩阵的一个槽位。
2. **挂载效率** — 属性如果挂不到几个句子，就丢弃该属性或该类。

此外，挂载必须 **有区分度**：要能区分属性属于谁，
例如 `birth(A)`、`date(EVENT_A)`——属性挂在具体实体上，
而不是笼统地属于某个大类。如果一句话含多实体且同属一个大类，
则调用 LLM 判断兜底。

### 改动
1. **新增 `src/attribute_schema.py`** — 属性表的运行期增量层。
   - `AttributeSpec` / `ClassSpec` / `AttributeSchema`：agent 的增量
     （新属性 + 新实体类），可 apply / save / load / export。
   - `ATTRIBUTE_CANDIDATE_LEXICON`：**有界**候选属性表
     （nationality / religion / cause_of_death / also_known_as /
     military_service / language / area / climate / dissolved / cause）。
     agent 不得凭空发明无界的属性词表。
   - `CLASS_CANDIDATE_LEXICON`：候选实体类表
     （FAC / PRODUCT / LAW / LANGUAGE / TIME）。
   - `apply_to_modules()` 就地修改 `sentence_graph` 的三张表
     （`ATTRIBUTE_DESCRIPTORS` / `ATTRIBUTE_NAMES` /
     `_ATTRIBUTE_TEMPLATES`）。**必须就地改**：`graph_builder` 与
     `stengraph_pipeline` 在 import 时就按名字绑定了这些对象，
     重新绑定模块属性会让它们继续指向旧列表。
   - `apply_to_registry()`：patch 已建好的 `AttributeRegistry`
     （它的 `_templates.copy()` 是浅拷贝，新类必须显式写入）。

2. **新增 `src/attribute_agent.py`** — agent 本体，闭环为
   **采样 → 检测缺口 → 提议 → 三准则把关 → 应用 → 重新挂载**。
   - `AttributeAgentConfig`：可调参数（轮数、阈值、LLM 上限）。
   - `QUESTION_TRIGGERS`：问题侧触发词表。属性缺口是在 **问句**
     上检测的（"When was X born" 问的是 `birth`，句子里并不含
     "born"），与 `sentence_graph` 里的句级词干表是两套东西。
   - **缺口检测**：
     - *缺类* — 锚实体的 spaCy 类型没有自己的模板，
       只能挂 `description` 兜底，不携带任何信号；
     - *缺属性* — 问句要的属性不在该实体的类模板里，且不在候选
       词表内则不许提议。
   - **三准则把关**（`_gate`）：
     1. 包容性 — 触发词/词干太少、descriptor 与已有属性重复
        （cos ≥ 0.80）→ 丢弃；
     2. 挂载效率 — 挂载句数 < `min_mount_count` 或全库占比 <
        `min_global_mount_rate` → 丢弃；
     3. 区分度 — 该属性在本类的 top-K 命中率必须比其它 **可能拥有
        该属性的类** 高出 `min_distinctiveness_margin`，否则它不区分
        任何东西 → 丢弃。
   - **度量必须复刻真实挂载**（`_measure`）：排序集合是实体自己的
     模板（真实挂载只允许挂模板里声明的属性），且**先加权再排序**
     （`description` 兜底权重 0.7，不能占掉 top-K 槽位）。
   - **LLM 只在两处兜底**，且都可关闭：
     - 同大类多实体的归属（"Washington and Lincoln" 这句事实属于谁）；
     - 缺口确认（检测基于触发词，可能是假阳性）。
   - agent **不改源码**：增量落盘为 JSON，`export_python()` 可导出
     成可粘贴的源码片段，由人决定是否固化。

3. **`src/graph_builder.py`** — `GraphBuilder.__init__` 新增
   `attribute_schema` 参数，在第一个容器创建**之前** apply，
   这样新属性/新类进入它派发的每一个模板。

4. **新增 `eval/attribute_agent_eval.py`** — 驱动脚本（采样参数、
   增量落盘、报告输出）。`--schema` 可载入已有增量继续往前滚。

5. **新增 `eval/attribute_agent_selftest.py`** — 43 项确定性自测，
   不依赖 spaCy / embedder / LLM / 数据集，锁死三条把关准则。

6. **新增 `eval/attribute_agent_smoke.py`** — 合成语料端到端冒烟测试。

### 跑前
属性表为静态常量，无缺口检测能力。

### 跑后
合成语料冒烟（`eval/attribute_agent_smoke.py`，n=4×2 轮）：
- 检出缺口 3 个：`PERSON::religion`、`PERSON::nationality`、
  `FAC`（缺类）
- 通过 2 个：`religion`（判给 NORP，margin 0.650）、
  `FAC` 缺类（`location` / `events` / `function` 挂载效率达标）
- 丢弃 1 个：`nationality` 对 PERSON — NORP 的命中率更高
  （0.750 vs 0.300），margin 为负，属性区分不出 PERSON。

自测 43 项全通过（`eval/attribute_agent_selftest.py`，不依赖
spaCy / embedder / LLM / 数据集）。

> 真实指标（EM / F1 / R@k）需在 HotpotQA 上跑 `quick20_eval.py`
> 对照；数据集不在仓库内（`.gitignore` 排除 `eval/data/`）。

### 实现中踩到的三个坑（都写进了 DESIGN.md）

1. **度量必须复刻真实挂载**。用"该句与 descriptor 的余弦"直接
   判定会系统性高估——真实挂载受模板限制、且 `description` 被降权
   到 0.7，两处都会改变 top-K 归属。改法：排序集合取实体自己的
   模板，**先加权再排序**，只取 top-K。
2. **owner 类必须由度量决定，不能假设**。缺口是在问句锚点上检测的，
   但属性不一定归该类所有（`religion` 对 PERSON 和 NORP 一样合适）。
   改法：在候选类里比"赢下多少个 top-K 槽位"，赢最多的成为 owner；
   平票时问句锚点优先（否则会按字母序把 `religion` 判给 NORP，
   而问句问的其实是人）。
3. **句子 ID 会跨图重复**。每次建图都从 `s_0001` 开始，直接累加
   会把同一张图的统计数 200 遍，所有全库指标都会算错。
   改法：profile 用 `"{qid}::{sid}"` 加命名空间。

### 结论
- 属性表从"写死的常量"变成"可被 agent 读写的运行期 schema"，
  滚动优化不必改源码。
- 关键设计取舍：**度量必须复刻真实挂载**。用"该句与 descriptor
  的余弦"直接判定会系统性高估——真实挂载受模板限制、且
  `description` 被降权，两处都会改变 top-K 归属。

## 改造 B: attribute_agent 接入 quick20_eval（一体化跑批）

### 目的
原先 `attribute_agent_eval.py` 和 `quick20_eval.py` 是两个互不相干的
脚本：agent 只产出属性增量，quick20 只测 EM/F1。**增量对检索指标
到底有没有正收益，无人测过** —— 只能靠人肉把 JSON 灌回源码，
再跑一次 quick20 对比。

改造目标：一条命令同时完成「滚动优化 → 应用增量 → 测 EM/F1」，
并且支持 **A/B**（同一份样本，增量前跑一次、增量后跑一次），
让属性的收益/代价可以直接量化。

### 改动
1. **`eval/attribute_agent_eval.py`** — 抽出可复用入口
   - `run_attribute_agent(questions, *, ...) -> AgentReport`：
     原来的 `main()` 逻辑整体下沉到这个函数，负责采样参数、
     构造 `AttributeAgentConfig`、跑 `agent.run()`、落盘
     report / schema / snippet。
   - `log_report(report)`：把原先散在 `main()` 里的报告打印
     抽成独立函数，供 quick20 直接复用。
   - 新增 `nlp` 入参：复用 quick20 已经加载好的
     `en_core_web_lg`，避免第二次加载 spaCy 模型。
   - `main()` 改为薄封装，只负责 argparse + 调 `run_attribute_agent`。
   - `run_attribute_agent` 的 `questions` 同时接受
     「原始 HotpotQA 记录」和「`load_questions()` 之后的 dict」，
     后者按 `qid` 键自动识别（quick20 传的是原始记录）。

2. **`eval/quick20_eval.py`** — 接入点
   - 新增 CLI：
     - `--attr-agent` —— 先跑 agent 并应用增量，再评测。
     - `--attr-agent-ab` —— A/B 模式：增量前跑一次（baseline），
       agent 跑完应用增量后再跑一次（treatment），最后打印
       EM/F1/R@k 的逐项差值。隐含 `--attr-agent`。
     - `--attr-agent-n` / `--attr-agent-rounds` /
       `--attr-agent-seed` —— agent 的采样参数（默认 20×10，seed 1234）。
     - `--attr-agent-schema` —— 从已有增量继续往前滚。
     - `--attr-agent-out` / `--attr-agent-report` —— 落盘路径。
     - `--attr-agent-no-llm` —— 关掉 agent 的 LLM 兜底。
     - `--attr-agent-dry-run` —— 只报缺口，不应用增量。
   - 把原本内联在 `main()` 里的评测循环抽成
     `_evaluate_sample(args, sample, nlp, client, offline_store)
     -> (summary, records)`。**关键点**：容器派发属性槽位时读的是
     `src.sentence_graph` 的模块级模板，所以"当前生效的属性表"
     就是 A/B 两次之间唯一变化的变量 —— baseline 在 agent 应用增量
     **之前**跑，treatment 在之后跑。
   - A/B 差值打印（`_log_ab_delta`）+ 落盘 `<out>_ab.json`，
     内含 baseline / treatment / delta 三段，以及 agent 侧的
     缺口数、接受数、接受的属性名与类名。
   - 主结果 JSON 增加 `attr_agent` 段，记录本次是否跑了 agent。

### 跑前
属性 agent 与 quick20 脱节，增量对 EM/F1 的影响**无数据**。

### 跑后
待跑（见下方"终端命令"）。

### 结论
- agent 的产出从"一个孤立的 JSON"变成"可被评测闭环验证的增量"。
- A/B 顺序是硬约束：baseline 必须在 agent 应用增量之前跑，
  否则两侧都用新表，delta 恒为 0。
- 改动时间：2026-10-29
- 改动目的：把属性滚动优化接进 quick20 评测闭环，使其可被指标验证
- 改动功能：新增 `--attr-agent` / `--attr-agent-ab` 等 10 个参数，
  抽出 `_evaluate_sample()` 与 `run_attribute_agent()` 两个可复用入口

## 改造 C: LLM 配置接入 llm_client（.env 自动加载）

### 目的
`src/llm_client.py` 的 `make_client()` 只读 `os.environ`，**从不加载
仓库根目录的 `.env`**。README 里让用户手动 `load_dotenv()`，但仓库里
没有任何脚本这么做。后果是：

- `make_client()` 返回一个 **disabled** 的 client；
- 所有依赖 LLM 的功能（实体抽取、答案抽取、agent 的缺口确认）静默降级
  成启发式回退；
- **日志上看不出来** —— client 是 disabled 而不是报错。

这直接毁掉上一条改造（B）的 A/B 测量：treatment 和 baseline 都没真正
用上 LLM，两边必然一模一样，delta 恒为 0。

### 改动
1. **`src/llm_client.py`**
   - 新增 `load_env_file(path=None)`：读 `.env` 并写入 `os.environ`，
     **不覆盖**已存在的变量（真实环境变量永远优先）。
   - 新增 `_parse_dotenv(text)`：内置的极简解析器（`KEY=value`、
     `export KEY=value`、引号剥离、行尾注释）。`python-dotenv` 装了
     就用，没装就用这个 —— 遵守"不引入新重型依赖"的项目规则，同时
     避免"可选依赖缺失 = 功能缺失"。
   - 新增 `_ensure_env_loaded()`：每进程只加载一次。
   - `make_client()` 与 `DeepSeekClient.__init__` 都调用它。
   - 新增三个自省接口：
     - `llm_available()` —— 有 key 或配了本地服务器 → True；
     - `local_llm_configured()` —— 是否指向本地 vLLM；
     - `describe_llm_config()` —— **脱敏**的一行配置摘要
       （端点 / 模型 / 有无 key，绝不输出 key 本身）。
2. **`eval/quick20_eval.py`** / **`eval/attribute_agent_eval.py`** —
   启动时打印 `LLM config: ...`，让"这次跑到底有没有用上 LLM"写在
   日志里。
3. **`.env`** — 新建（已 gitignore），带中文注释说明两种配置方式。
4. **`.env.example`** — 补齐本地 vLLM 的三个变量。
5. **`requirements.txt`** — 把 `python-dotenv` 标为 optional。

### 跑前
`make_client()` 读不到 `.env` → client disabled → LLM 路径静默失效。

### 跑后
- `.env` 存在 → `make_client().enabled == True`，key 正确解析。
- 优先级验证：进程环境变量 > `.env`（已测）。
- 本地 vLLM 路径：`STENRAG_LLM_BASE_URL` 一设 → 走本地 + 占位 key
  （已测）。
- 真实调用打到 DeepSeek 并返回 **401**（key 还是占位符 `sk-your-...`
  未替换），说明请求链路本身是通的；401 被 `answer_extractor` 捕获后
  返回 `""`，优雅降级不崩。

### 结论
- "LLM 有没有真的在用"必须是**日志里看得见**的量，否则 A/B 数字不可信。
- 可选依赖不能悄悄变成功能缺失 —— 故内置 fallback 解析器。
